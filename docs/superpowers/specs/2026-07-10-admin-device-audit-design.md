# 管理端设备来源审计

## 问题

当前管理端审计日志主要依赖来源 IP。多台设备共用同一公网出口时 IP 相同；设备经过 Shadowrocket、Xray、VPN 或其他代理时，服务端只能看到代理出口 IP。现有统一审计页还只有系统设置日志保存来源 IP，核验、核验失败和退款日志没有保存来源信息，票种修改也缺少统一的设备来源审计。

目标是在不把设备标识当作认证凭证的前提下，为每次管理写操作记录可信来源 IP、稳定浏览器设备编号、登录会话和浏览器环境，从而区分共用网络或代理出口下的不同管理设备。

## 范围

- 管理员首次登录时由后端生成随机设备令牌，并通过独立 Cookie 保存。
- 后端只保存设备令牌的不可逆摘要，并用摘要前缀生成可展示的设备编号。
- 每条受支持的管理审计记录固化操作时的来源 IP、设备编号、管理会话 ID、User-Agent 和 request ID。
- 统一审计页展示 `来源 IP / 设备编号`，详情展示完整来源上下文。
- 覆盖系统设置、票种新增或修改、票种上下架或删除、核验入园、撤销核验、核验失败和退款操作。
- 旧审计记录继续可查询，缺少的新字段显示为“历史记录未采集”。
- 提供 openGauss 兼容的数据库迁移，并同步更新基线 schema。

## 不在范围

- 不使用浏览器指纹、Canvas 指纹或第三方设备识别服务。
- 不保证识别物理硬件；清除 Cookie、更换浏览器或使用无痕窗口会产生新的设备编号。
- 不尝试从浏览器获取局域网 IP、MAC 地址、序列号或其他硬件标识。
- 不把设备编号用于认证、授权、风控放行或绕过密码与 CSRF 校验。
- 不自动修改其他管理设备上的 Shadowrocket、VPN 或系统代理配置。

## 设备标识

设备 Cookie 使用独立名称 `scenic_admin_device`。后端在管理员登录成功时执行以下逻辑：

1. 如果请求携带格式有效的设备令牌，则复用该令牌。
2. 如果设备令牌缺失或格式非法，则使用 `secrets.token_urlsafe(32)` 生成新令牌并写入响应 Cookie。
3. Cookie 使用 `HttpOnly`、`SameSite=Lax`、根路径、365 天有效期和与管理 session 相同的 `Secure` 策略，不设置为认证 Cookie。
4. 审计记录只保存 `SHA-256` 摘要的前 24 个十六进制字符作为设备编号，不保存原始令牌。

设备编号在同一浏览器 Cookie 存续期间保持稳定。设备令牌泄露不会赋予登录权限，但仍按伪匿名标识处理，不在日志和 API 中返回原始值。

## 来源 IP 信任边界

生产请求链为 Nginx 到监听在 `127.0.0.1:8000` 的 FastAPI。Nginx 必须覆盖来源头，而不是追加客户端提供的值：

```nginx
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $remote_addr;
```

后端仅在直接连接地址属于本机回环地址时读取 `X-Forwarded-For` 或 `X-Real-IP`，否则使用直接连接地址。所有候选值继续使用标准 IP 解析器校验，非法值不入库。

来源 IP 表示服务端实际看到的公网出口。设备经过代理时可以是代理 IP；设备编号用于区分共用该出口的浏览器实例。

## 审计上下文

后端提供一个小型共享函数，从已认证的管理请求生成不可变审计上下文：

- `source_ip`：可信来源 IP，可为空。
- `device_id`：设备摘要前缀，可为空，仅兼容历史或异常请求。
- `admin_session_id`：当前管理 session 的数据库 ID。
- `user_agent`：请求头中的 User-Agent，截断到数据库字段上限。
- `request_id`：现有请求链路编号。

业务服务在完成权限校验后生成上下文，并与原有业务审计数据在同一事务中写入。审计字段记录操作发生时的值，不依赖后续查询 session 表，避免 session 失效或清理改变历史记录。

## 数据模型

核验、核验失败和退款审计表统一增加以下可空字段：

- `source_ip VARCHAR(64)`
- `device_id VARCHAR(32)`
- `admin_session_id BIGINT`
- `user_agent VARCHAR(512)`

系统设置审计表复用现有 `source_ip`，只补充其余字段。核验、核验失败和退款审计表补齐全部字段。票种管理新增专用业务审计表，记录票种 ID、操作类型、操作说明、管理员身份和相同来源上下文。

字段保持可空，以兼容现有数据和迁移前记录。设备编号和 session ID 暂不建立独立设备注册表，也不提供设备管理页面；当需要管理员命名、禁用或审批设备时再扩展。

## 接口与界面

统一审计接口在现有记录上增加：

- `sourceIp`
- `deviceId`
- `adminSessionId`
- `userAgent`

前端列表的“请求来源”显示 IP 和短设备编号。详情面板分别显示来源 IP、设备编号、登录会话和浏览器环境。缺失字段显示“历史记录未采集”，不伪造默认值。

设备 Cookie 完全由后端管理，前端不读取、不生成，也不需要把设备标识放入请求体或自定义请求头。

## 安全与隐私

- 客户端提供的 `X-Forwarded-For` 不能覆盖 Nginx观察到的来源地址。
- 原始设备令牌不写入数据库、普通日志、响应 JSON 或审计导出。
- 设备编号不能单独用于封禁或放行账号，因为用户可以清除 Cookie。
- User-Agent 是不可信展示数据，必须限制长度并通过现有前端转义机制显示。
- 审计详情仍受管理端会话和现有权限校验保护。
- 后续启用 HTTPS 时，生产 Cookie 必须启用 `Secure`；当前策略与 session Cookie 保持一致以避免 HTTP 环境下设备编号反复变化。

## 错误与兼容

- 设备 Cookie 缺失或非法不阻止管理员登录；后端生成新的合法设备令牌。
- 无法解析来源 IP 时保存空值，不使用未经校验的原始字符串。
- 数据库迁移前的历史记录保持可读。
- 审计上下文写入失败时，业务写操作必须回滚，避免出现“操作成功但没有审计”的安全缺口。
- 生产仍运行 openGauss，迁移不使用未经验证的 PostgreSQL 专有语法。

## 验收

- 同一浏览器连续登录产生相同设备编号，不同 Cookie 容器产生不同设备编号。
- 清除设备 Cookie 后产生新设备编号，原有登录授权逻辑不受影响。
- 同一公网 IP 下的两个浏览器可以通过设备编号区分。
- 经过代理时审计显示代理出口 IP，但仍能通过设备编号区分浏览器。
- 直接访问后端或伪造来源头不能让客户端指定任意审计 IP。
- 系统设置、票种管理、核验、撤销核验、核验失败和退款操作均写入来源上下文。
- 旧审计记录在统一审计页正常显示且明确标记缺失字段。
- 后端定向测试、完整后端测试、前端构建和生产部署核验 Skill 的管理端写操作烟测全部通过。
