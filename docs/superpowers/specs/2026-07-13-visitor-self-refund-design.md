# 游客整单自助退款设计

## 背景与目标

系统已有管理员整单和部分模拟退款，能在同一事务内更新订单、票项、支付记录、时段库存和退款审计。本功能让已登录游客对自己的已支付未使用订单执行整单自助退款，并复用现有退款状态机与事务。

## 范围

包含：

- 游客整单模拟退款。
- 订单归属、CSRF、状态和退款时限校验。
- 订单、票项、支付、库存与审计原子更新。
- 游客退款审计操作人模型。
- 移动端退款入口、二次确认和已退款状态。
- 旧库 SQL 迁移、实际数据库备份、迁移执行和真实库回放。

不包含：游客部分退款、已核销退款、人工审批、真实支付渠道退款和自然语言退款规则解析。

## 方案

采用“共享退款事务，扩展审计操作人”。现有整单退款仓储事务接受管理员或游客操作人上下文；管理员 API 保持现有权限和响应，新游客 API 先校验会话、归属与截止时间，再进入相同的锁定事务。

不单建游客退款事务，避免复制金额、库存和状态逻辑；不做管理员审批流，避免引入额外申请表和审批状态机。

## API 契约

新增 POST /api/orders/{order_no}/refund。

- 必须是已登录游客并携带会话绑定 CSRF header。
- 订单必须属于当前游客。
- 请求体仅允许可选 reason，trim 后最长 100 字符，空白归一化为 null。
- 客户端不能提交退款金额、订单状态、支付状态、票项状态、库存数量或操作人字段。
- 游客订单 DTO 新增后端派生的 canSelfRefund 和 refundDeadline，前端不自行重建可退规则。
- 成功响应复用游客订单详情 DTO，返回 REFUNDED 订单，不暴露审计内部字段。

错误码：

- 401 AUTH_REQUIRED：未登录。
- 404 ORDER_NOT_FOUND：订单不存在或不属于当前游客，避免泄露其他人订单是否存在。
- 409 ORDER_ALREADY_REFUNDED：已全额退款。
- 409 ORDER_NOT_REFUNDABLE：订单、支付或票项状态不可退。
- 409 ORDER_REFUND_DEADLINE_PASSED：已超过自助退款时限。
- 422 VISITOR_REFUND_INVALID：请求格式不合法。

## 业务规则与事务

自助退款必须同时满足：

1. order_status = PAID。
2. payment_status = PAID。
3. 所有票项均为 UNUSED。
4. 存在 SUCCESS 支付记录。
5. 当前游客拥有该订单。
6. 当前时间不晚于最早游玩日期前一天 18:00。

截止时间按 Asia/Shanghai 计算，作为结构化业务规则，不动态解析 refund_rule 文本。

后端在同一数据库事务中锁定订单、票项和成功支付记录；根据 final_price 计算退款金额；将订单、支付和票项更新为 REFUNDED，paid_amount 置零；按票项回补 time_slot_quota.quota_sold；写入 FULL 退款审计。并发重复请求最多一次成功。

## 审计与数据库迁移

schema.sql 中的 refund_audit_log 扩展为同时支持管理员和游客操作人：

- 新增 operator_type VARCHAR(20) NOT NULL，允许 ADMIN 或 VISITOR。
- 新增 operator_visitor_id BIGINT，外键指向 visitor(id)。
- operator_admin_user_id 改为可空。
- 保留 operator_username 和 operator_display_name 作为审计快照。
- 新增互斥约束：ADMIN 必须仅有 operator_admin_user_id，VISITOR 必须仅有 operator_visitor_id。
- 新增游客操作人与创建时间索引。

必须新增幂等旧库迁移 database/migrations/2026-07-13-add-visitor-refund-audit-actor.sql：

1. 新增 operator_type 并把历史记录回填为 ADMIN。
2. 新增可空 operator_visitor_id 和外键。
3. 取消 operator_admin_user_id 非空限制。
4. 增加操作人类型与互斥约束。
5. 增加必要索引。

实施时必须先用 pg_dump -Fc 备份当前 scenic_ticket，再用 psql -v ON_ERROR_STOP=1 -1 在事务中执行迁移。执行后验证字段、外键、互斥约束、索引、历史记录回填，并通过真实游客会话回放退款。

## 前端交互

- 可退的已支付订单详情显示次要操作“申请退款”。
- 超过时限时显示“已过自助退款时间，请联系客服”。前端判断仅用于展示，后端仍重新校验。
- 二次确认弹窗展示订单号、后端订单金额、退款截止时间、票码失效提示和可选退款原因。
- 确认按钮使用危险色，提交中禁用重复点击。
- 成功后关闭弹窗，刷新列表与详情，显示“退款成功”且不再展示可用票码。
- 订单筛选增加“已退款”，393×852 下保持等宽可点击且无溢出。
- API 错误在弹窗内显示错误码和请求编号，可重试。

## 测试与验收

后端覆盖：未登录、缺少 CSRF、越权、已退款、未支付、部分退款、已核销、支付记录缺失、超时、并发重复、成功事务以及管理员退款回归；同时验证 OpenAPI、DTO 防泄露和 schema 契约。

前端覆盖：退款入口可见性、弹窗信息、成功刷新、已退款筛选、票码隐藏、错误展示和 iPhone 15 Pro 无溢出。

真实库验收：备份文件非空；实际字段、约束和索引与 schema 一致；历史记录回填为 ADMIN；真实游客会话可退款并读取退款后详情。

## 验收标准

- 游客无法退其他人订单。
- 符合状态和时限的订单只成功退款一次。
- 退款后金额、票项、支付、库存与审计一致。
- 游客和管理员退款操作人可明确区分。
- 移动端可完成二次确认，成功后立即显示已退款。
