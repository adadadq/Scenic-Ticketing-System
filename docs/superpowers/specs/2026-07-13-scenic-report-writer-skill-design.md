# 景区票务课程设计报告 Skill 设计

日期：2026-07-13

## 目标

创建项目本地 Skill `scenic-report-writer`，专门用于景区票务系统数据库课程设计报告的实质性新写、重写、同步和审查。

Skill 必须同时服从两类事实源：

1. 当前 FastAPI + React 主工程及其数据库、接口、测试和验收证据；
2. 学校提供的数据库课程设计报告模板及其章节、图表、代码和成员署名要求。

核心结果是：项目发生实质变化后，下一次报告写作先同步事实，再修改报告；没有项目证据的内容不得写成已实现。

## 方案比较

### 方案 A：每次报告编辑都自动触发

优点是约束最严格。缺点是改错别字、页码、姓名或字体时也会加载项目上下文，成本过高，不符合用户要求。

### 方案 B：只在用户显式调用时触发

优点是简单。缺点是用户可能忘记调用，新增章节或项目更新后的报告同步容易绕过事实核验。

### 方案 C：语义触发并排除小幅修改

在新写章节、实质性改写、项目同步、数据库/接口/测试描述变更和全文审查时触发；错别字、标点、排版、姓名学号、页码等小幅修改不触发。

采用方案 C。它能保证事实性写作受控，同时避免小改动加载大型项目上下文。

## 安装位置与路由

Skill 放在当前主工程：

```text
.skills/scenic-report-writer/
```

在主工程 `AGENTS.md` 增加本地路由：

- 实质性创建、重写、同步或审查数据库课程设计报告时使用该 Skill；
- 仅修改错别字、标点、字体、行距、页码、姓名学号、图表编号，且不改变技术事实时不触发；
- 若局部句子修改改变功能、表结构、接口、状态、测试结论或安全结论，则仍视为实质性修改并触发。

## Skill 目录

```text
.skills/scenic-report-writer/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── scripts/
│   └── check_report_sync.py
└── references/
    ├── source-map.md
    └── template-rules.md
```

不复制项目源码和报告模板，避免形成过期副本。

### SKILL.md

保持为短流程说明，负责：

- 判断是否属于小幅修改；
- 确定事实源优先级；
- 执行项目同步检查；
- 指定按章节取证的写作流程；
- 强制证据、模板和禁止编造门槛；
- 调用本地 `docx` Skill处理Word文件，但只修改用户指定范围。

### references/source-map.md

记录报告章节到项目证据的路由，例如：

- 项目概览：`README.md`、`docs/architecture.md`；
- 数据库设计：`database/schema.sql`、迁移和schema测试；
- 安全：`docs/backend-security-audit.md`、安全测试；
- 游客、订单、核销、退款、报表、导出：对应 API、Service、Repository、前端功能和测试；
- 总览：项目外层的《景区票务系统-数据库课程设计报告写作总览.md》。

这里只保存路径和读取策略，不复制1096行总览全文。

### references/template-rules.md

固化模板中的稳定要求：

- 报告章节结构；
- 数据库设计必须按概念、逻辑、物理、安全与完整性顺序；
- 详细设计按成员模块署名；
- 每个模块必须有文字、流程图、实际截图、少量关键代码和解释；
- 测试采用场景、等价类、边界值、状态转换和回归测试；
- 最终正文完成后重新生成目录；
- 附录至少5份会议记录。

### scripts/check_report_sync.py

脚本只做确定性检查，不自动编写报告。它扫描当前事实源并生成或比较指纹：

- `README.md`；
- `database/schema.sql` 与 `database/migrations/`；
- `backend/app/api/`、`schemas/`、`services/`、`repositories/`、`core/`；
- `backend/tests/`；
- `frontend/src/features/`、`frontend/src/shared/api/`；
- 架构、安全、验收、接口契约和决策日志。

输出状态：

```text
in-sync
changed
baseline-missing
```

输出还包含发生变化的文件路径。指纹状态保存在项目本地、可由 Skill维护的文件中，不把源码内容复制进状态文件。

## 触发边界

### 不触发

- 修正错别字、标点、空格；
- 修改字体、字号、行距、页边距和页码；
- 替换姓名、学号、日期；
- 修正图号、表号或交叉引用；
- 不改变技术含义的单句润色。

### 必须触发

- 新写一个章节或小节；
- 重写摘要、需求、数据库设计、详细实现、测试或改进思路；
- 项目更新后同步报告；
- 修改功能、角色、接口、数据库表、字段、约束、索引、状态机、安全或测试结论；
- 新增或替换流程图、ER图、代码证据或运行截图；
- 全文模板合规、事实一致性或防编造审查。

判断原则：改动是否可能改变读者对“系统实际实现了什么”的理解。若会改变，则触发。

## 工作流

### 1. 范围判断

先判断任务是否仅为小幅修改。小幅修改直接按用户指定范围处理，不加载该 Skill 的完整项目审计流程。

### 2. 同步检查

实质性任务先运行 `check_report_sync.py`。

- `in-sync`：继续按当前总览取证；
- `changed`：读取变化文件及关联测试，更新《景区票务系统-数据库课程设计报告写作总览.md》，再改报告；
- `baseline-missing`：建立当前事实基线后再写报告。

指纹只能提示文件变化，不能证明功能已经完成。所有新增事实仍需源码、测试或实际页面证据。

### 3. 章节取证

根据 `source-map.md` 只读取当前章节需要的文件。证据优先级：

1. 当前运行代码和数据库结构；
2. 自动化测试、契约和实际运行结果；
3. README、验收、安全和架构文档；
4. 设计稿和计划文档；
5. 聊天记录。

计划文档不能单独证明已实现。

### 4. 写作

按 `template-rules.md` 和目标章节结构编写。缺少截图、流程图或测试结果时使用明确占位符，不伪造材料。

关键代码只截取核心逻辑，注明文件路径并解释输入、校验、数据库操作、输出、安全和异常处理。

### 5. Word编辑

修改 `.docx` 时同时使用学业文件本地 `docx` Skill：

- 保留模板版式和用户已有手工修改；
- 只改用户指定章节；
- 完成后做文本回读和视觉验证；
- 全文完成后更新目录、图号、表号和交叉引用。

### 6. 完成前审查

逐项检查：

- 每项技术结论是否有证据；
- 表名、字段、状态、接口和角色是否与当前项目一致；
- 是否把mock或disabled provider写成真实集成；
- 是否把设计稿或计划写成完成情况；
- 是否符合模板章节和模块署名要求；
- 是否泄露手机号、证件号、Cookie、CSRF、密码、连接串或密钥。

## 固定禁止项

除非当前项目未来确实实现并通过证据核验，否则禁止写成当前能力：

- 真实微信、支付宝、银联或其他资金支付；
- 真实短信验证码；
- Redis、Celery、RabbitMQ等外部限流或队列；
- OSS、S3等对象存储；
- 邮件、Webhook或外部告警平台；
- 实体闸机和扫码硬件；
- 公告数据库持久化；
- 未存在的存储过程或触发器；
- 未运行的性能数据、用户规模、测试通过结果或生产指标。

现有边界包括：`PAYMENT_PROVIDER=mock`、`SMS_PROVIDER=disabled`、登录限流为`memory`、公告为进程内存、导出存储为`local`、队列为`database`、外部告警为`disabled`。这些边界在项目变化后必须重新核验。

## 错误处理

- 事实源互相冲突：停止写作，列出冲突和证据，优先验证运行代码和测试。
- 项目变化但测试未更新：只描述代码中可确认的结构，不声称功能已验收。
- 缺少截图或运行环境：插入具体占位符，不生成假截图。
- 用户要求写不存在的功能：明确标为规划或改进方向，不伪装成现状。
- 模板与用户已编辑文档冲突：保留用户手工现状，只在指定范围内调整，并说明冲突。

## 验证

创建后执行：

1. `skill-creator` 的 `quick_validate.py`；若本机缺少PyYAML，改用已有YAML环境或手工检查frontmatter和目录结构；
2. 运行同步脚本的三个分支测试：无基线、无变化、有变化；
3. 检查`agents/openai.yaml`与Skill触发边界一致；
4. 用三个示例进行前向验证：
   - “把报告中的一个错别字改掉”应不触发完整审计；
   - “根据最新schema重写数据库设计”应先同步再写；
   - “写已经接入微信支付”应拒绝虚构并改写为mock现状或改进方向。

## 验收标准

- 小幅修改不会触发该Skill；
- 实质性报告任务能自动命中；
- 项目事实源变化会被同步检查发现；
- 报告修改前会先更新事实总览；
- 模板要求被稳定执行；
- 没有证据的功能不会被写成已完成；
- Word局部修改保留用户已有内容和模板版式；
- Skill目录简洁，不复制大段项目源码或生成无关文档。
